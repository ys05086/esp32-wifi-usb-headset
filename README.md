# ESP32 Wi-Fi USB Headset

**Wi-Fi ↔ USB 오디오 브리지.** ESP32-S3가 통화용 휴대폰에 USB 헤드셋으로 꽂히고, 마이크로 보낼 소리와 상대방 소리를 Wi-Fi로 PC와 주고받습니다.

- [`firmware/`](firmware/): ESP32-S3 펌웨어. USB Audio Class 2 헤드셋 + Wi-Fi UDP 오디오.
- 저장소 루트: Windows 앱 **ESP32 Call Bridge**. PC 마이크·헤드폰 ↔ 보드.
- [PROTOCOL.md](PROTOCOL.md): 보드와 주고받는 UDP 형식. 다른 프로그램도 이 형식으로 보내면 됩니다.

## ESP32 Call Bridge (Windows)

**휴대폰 통화를 PC 마이크와 헤드폰으로 이용하는 실시간 오디오 브리지입니다.** PC와 ESP32는 Wi-Fi/LAN으로 연결하고, ESP32는 휴대폰에 USB 헤드셋으로 연결합니다. 내 목소리는 휴대폰으로 보내고, 상대방 소리는 PC로 받아 재생합니다.

전화 걸기·받기와 통화 연결은 휴대폰의 전화/통화 앱에서 합니다. PC 앱은 마이크와 듣는 장치를 선택하고 양방향 오디오를 전달합니다. USB 통화 라우팅은 휴대폰과 통화 앱의 지원에 따라 달라집니다.

```text
PC 마이크 → PC 앱 → Wi-Fi → ESP32 → USB → 휴대폰 통화
PC 헤드폰 ← PC 앱 ← Wi-Fi ← ESP32 ← USB ← 상대방 소리
```

PC에서 사용할 마이크와 듣는 장치를 선택하면 됩니다.
ESP32의 **USB** 포트를 통화용 휴대폰/태블릿에 연결합니다. COM은 펌웨어 관리용입니다.

현재 실험 버전입니다. PC 프로그램의 빌드·실행·패킷 검사는 통과했지만, ESP32의 양방향 동시 처리에서는 간헐적인 USB 오디오 끊김이 남아 있습니다.

## 실행

처음 사용하는 보드는 먼저 [펌웨어 설치 안내](FIRMWARE_INSTALL.md)를 따라 준비하세요. COM/USB 포트 구분, 최초 설치·업데이트, Wi-Fi 설정과 기기별 확인 절차가 있습니다. 펌웨어 소스는 [firmware/](firmware/)에 있고, 빌드 결과는 Actions의 **Firmware** 실행에서 받습니다. 배포 라이선스 확인 현황은 [LICENSING.md](LICENSING.md)에 정리되어 있습니다.

이 저장소에서 직접 작성한 PC 앱 코드와 문서는 [MIT License](LICENSE)로 제공합니다. 외부 소프트웨어와 원문 고지는 각자의 라이선스를 유지하며 [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md) 및 `licenses/`를 참고하세요. 전체 바이너리 배포 조건 검토는 별도로 진행 중입니다.

1. 배포 ZIP 전체를 풀고 `ESP32CallBridge.exe`를 실행합니다. `_internal` 폴더도 함께 필요합니다. Python 설치는 필요 없습니다. 이전 버전 설정은 기존 실행 폴더의 `settings.json`을 새 실행 폴더로 복사하면 이어서 사용할 수 있습니다.
2. PC와 ESP32를 같은 공유기에 연결합니다. ESP32는 2.4 GHz를 사용하며, PC는 같은 LAN의 유선/5 GHz도 가능합니다.
3. 보드 설정 페이지에 표시된 `router_ip`를 입력합니다. 초기 설정은 Wi-Fi `ESP32-Headset` / `esp32headset`, 브라우저 `http://192.168.4.1`입니다.
4. **내 목소리**에서 PC 마이크, 오디오 인터페이스 또는 가상 케이블의 녹음 장치를 고릅니다.
   WASAPI 장치가 위쪽에 표시되며, 다른 드라이버 방식으로만 보이는 가상 케이블도 고를 수 있습니다. 이름 뒤의 WASAPI/MME/DirectSound/WDM-KS는 장치 접근 방식입니다.
5. **상대방 소리**에서 PC 이어폰/헤드폰을 선택하고 연결 시작을 누릅니다.
6. 휴대폰에서 전화를 걸거나 받고 USB 헤드셋으로 통화합니다. 통화 앱별 실제 라우팅은 기기에서 확인해야 합니다.

듣기 버퍼는 기본 80 ms이며, 연결 전에 40/80/120 ms 중 선택할 수 있습니다. 기존 40 ms보다 기본 듣기 지연이 약 40 ms 늘어나는 대신 짧은 패킷 도착 지연을 더 흡수합니다. 늦게 도착한 패킷은 재생 기한 전까지 순서를 복원하며, 단일 버퍼 부족 뒤에는 바로 재생을 재개할 수 있습니다. 긴 중단은 다시 버퍼를 채우며 300 ms 이상 오래된 데이터는 버립니다. 지속적인 장치 클럭 차이를 자동 보정하는 기능은 아직 없습니다.

실제 끊김이 들리면 **진단 저장**을 누르세요. 음성 녹음 없이 장치 이름·샘플레이트·수신 도착 간격·순서 복원·버퍼 부족·입출력 장치 오류·보드 카운터를 JSON으로 저장합니다. ‘보드 버퍼 부족’은 송신 경로, ‘듣기 버퍼 부족’은 수신 재생 경로입니다. 숫자가 0이어도 보드의 USB 오디오 데이터 자체가 깨끗하다는 보장은 아닙니다.

보드 설정 페이지의 **USB compatibility**(이전 표시: USB call device)는 USB 케이블로 연결한 기기의 호환성 설정입니다.
PC 앱의 주소 아래에도 **현재 USB 모드**가 표시됩니다. 보드에서 실제 적용 중인 Standard / Apple 값을 약 3초마다 읽으며, 설정을 저장했더라도 재부팅 전에는 기존 모드가 표시됩니다. 상태 조회는 오디오 처리와 별도 스레드에서 실행됩니다. 응답 실패 시 확인 불가로 바뀌고, 진단 JSON에는 마지막 조회 시각과 보드의 USB 전송 통계도 포함됩니다.
Apple은 Apple 호환 프로필, Standard는 Windows 호환 프로필이며 운영체제 전용 모드는 아닙니다. 사용자는 Apple 설정에서도 Galaxy가 작동한다고 보고했습니다. 이미 작동하는 설정은 유지하세요. 변경해 저장한 뒤에는 **USB와 COM을 모두 분리**해 전원을 끄고 다시 연결해야 적용됩니다.
Wi-Fi 클라이언트의 OS와는 무관합니다. 기본값은 Standard이며 실제 통화와 장시간 안정성은 기기별 검증 대상입니다.

상대방 소리를 마이크/가상 케이블로 다시 보내지 마세요. 보드 하나에는 송신 프로그램 하나만 연결합니다.
전송을 중지한 후 다른 클라이언트를 연결하세요. 동일 LAN의 신뢰할 수 있는 기기끼리 쓰는 실험용 UDP 전송입니다.

주소와 장치 이름은 실행 파일 옆 `settings.json`에 저장됩니다. 장치가 연결된 뒤 앱을 실행하세요.
현재 양방향 펌웨어가 필요합니다. 예전 마이크 전용 펌웨어는 새 클라이언트에 응답하지 않습니다.
오디오 형식은 48 kHz PCM16이며 송신/수신 네트워크 오디오는 각각 모노입니다.
입출력 장치는 지원 형식을 자동 확인합니다. 48 kHz를 지원하지 않는 캡처보드 등은 기본 샘플레이트(예: 96 kHz)로 열고, 스트리밍 리샘플러로 네트워크 형식과 변환합니다. 상태란에 실제 입출력 샘플레이트가 표시됩니다. 변환 시 필터 지연과 입력 버퍼가 추가됩니다.

## 보내는 음질 · AAC 비교

**보내는 음질…**에서 연결을 중지한 상태로 설정하고 저장한 뒤 다시 연결합니다. 설정은 실행 파일 옆 `settings.json`에 저장됩니다. 기본값은 기존 경로인 **원음 PCM**이며, **AAC 압축·복원**을 고르면 보내는 음성에만 적용됩니다.

- 샘플레이트: 16 / 24 / 32 / 44.1 / 48 kHz.
- AAC-LC 목표 비트레이트: 16 / 24 / 32 / 48 / 64 / 96 / 128 / 160 / 192 kbps. 16 kHz에서는 최대 96 kbps, 24 kHz에서는 최대 128 kbps만 표시합니다. 실제 평균 비트레이트는 입력에 따라 달라지며 진단에 기록됩니다.
- 처리 경로: 입력 장치 → 48 kHz PCM → 선택한 샘플레이트로 AAC 인코딩·디코딩 → 48 kHz PCM → ESP32. 별도의 코덱 작업 스레드와 제한된 큐를 사용합니다. 마이크 콜백에서 AAC 처리나 외부 프로그램을 실행하지 않습니다.
- 보드 USB 및 Wi-Fi 형식은 계속 48 kHz / 모노 PCM16입니다. 이 기능은 전송량을 줄이거나 보드 클럭을 바꾸지 않습니다. 통화·메신저 앱 자체의 녹음 인코더도 제어하지 않으며, 그 앱으로 다시 녹음하면 추가 압축될 수 있습니다.
- AAC 프레임 준비와 복원에는 수십~수백 ms의 추가 지연이 생깁니다. 낮은 샘플레이트는 같은 1,024샘플 프레임을 모으는 시간이 더 길어질 수 있습니다. 상태창의 AAC/송신 대기는 현재 큐와 처리량으로 계산한 추정치이며 전체 통화 지연은 아닙니다. 연결 중 설정 변경은 막고, 음소거는 이미 준비된 AAC 출력에도 즉시 적용합니다.

AAC 런타임은 실행 폴더에 포함되므로 별도 FFmpeg/Python 설치가 필요 없습니다. 음성 파일은 자동 저장하지 않습니다. `--quality-self-test REPORT.json`은 합성 신호로 번들 인코더·디코더를 검사하며 마이크나 네트워크를 열지 않습니다.

40개 노출 설정 조합의 실제 AAC 압축·복원, 출력 길이, 비트레이트 적용과 대역 제한, 기존 PCM 보존, 작업 종료/오류, 5개 샘플레이트별 가상 2분 송신 검사 등 22개 자동 테스트를 통과했습니다. 실제 PC 스케줄링, ESP32/폰 녹음 음질과 장시간 통화는 별도 확인이 필요합니다. 버퍼 부족으로 생긴 끊김을 AAC가 해결한다는 의미는 아닙니다.

## 개발

```powershell
python -m pip install -r requirements.txt
python -m unittest test_protocol.py
python app.py
python -m pip install pyinstaller==6.22.3
python -m PyInstaller --noconfirm --windowed --onedir --name ESP32CallBridge app.py
```

`app.py --self-test REPORT.json`은 숨겨진 창을 만들고 오디오 장치 열거 결과를 저장한 뒤 종료합니다. 녹음/재생은 시작하지 않습니다.
`app.py --audio-self-test REPORT.json`은 저장된 입출력 장치를 실제 작업 스레드에서 짧게 열고, 로컬 UDP 테스트 서버로 송신을 검증합니다. 출력은 무음이며 음성 파일을 저장하거나 실제 보드로 전송하지 않습니다. Windows 작업 스레드는 WASAPI 시작 전에 COM을 초기화하고 스트림 종료 후 해제합니다.

## 검증 범위

패킷 유효성, 세션 분리, 시퀀스 손실/재정렬, 버퍼 만료는 단위 검사합니다.
가상 시간 30분 동안 주기적으로 최대 60 ms 늦는 패킷을 넣는 회귀 검사도 포함합니다. 실제 Wi-Fi/USB 장치나 장시간 통화를 검증한 결과는 아닙니다.
ESP32 펌웨어와 실물 검사 스크립트는 [firmware/](firmware/)에 있습니다.

이 저장소는 PC 앱과 ESP32 펌웨어를 함께 담습니다.
GitHub Actions의 **ESP32 Call Bridge Windows**에서 실행 ZIP을 받을 수 있습니다.

Adaptive 실험 펌웨어의 활성 모드도 `Adaptive · 피드백 없음 (실험)`으로 표시합니다. 선택은 보드 웹페이지에서 하며 재부팅 후 적용됩니다. 이 클라이언트 업데이트는 오디오 송수신 처리를 변경하지 않습니다.
